# Technical and product audit findings

Severity reflects user/security/release impact. Items marked **verified** are grounded in inspected source or a probe; deployment/device behavior is explicitly marked unverified.

| Severity | Finding and evidence | Affected areas / impact | Root cause and action | Validation needed |
|---|---|---|---|---|
| Critical | **Client gateway credential is hard-coded.** `apiClient.js` constructs `X-Gateway-Key` from a constant. | Every gateway call; public APK/source can be reverse engineered and the credential reused outside the app. | Shared secret is distributed as client code. Design server-side user/session auth, abuse controls and per-client rate limits; rotate key with an approved overlap plan. Do not just delete the header or existing clients may fail. | Inspect production gateway auth and access logs; rotate; confirm old credential rejected and app flows still work. |
| Critical | **Android signing material is present in public Git history.** The current local `origin/main` base commit tracks `release.keystore` and `keystore_base64.txt`; this turn removed both paths from the Git index while preserving the local files. This does not erase public history or caches. | APK integrity, account continuity, and all future app updates if the same key is used. | Private signing material was committed to a public source repository. Treat it as compromised. Verify whether it signed the submitted APK; if yes, assess recovery/package identity consequences and reissue under an approved migration plan. Store future signing inputs only in restricted CI secrets. | Compare certificate fingerprints locally against the submitted APK without printing or uploading private keys. Review GitHub history/caches and rotate or migrate signing only through the owner's release process. |
| High | **The published workflow can create a public release on any push to `main`.** `.github/workflows/build.yml` in the current public commit runs a signed build and `gh release create` for both `push` and manual dispatch. The current visible releases section is empty, so no prior release was observed. | An ordinary source/README push can publish an APK without a separate release decision, violating the project's release approval rule. | Build and publishing share one job and trigger. I changed the local workflow so pushes validate only; a signed build/release requires manual dispatch with `publish_release=true`, and write permission is limited to that job. The local fix has not been pushed, so the public workflow remains unsafe until the change is approved and published. | YAML structure/gate check passed locally. Configure required reviewers on the `production-release` GitHub environment, then review the workflow on GitHub before any main-branch push. Do not run a manual release workflow without explicit approval. |
| High | **The current lockfile has unresolved npm advisories.** A live registry-backed `npm audit --json` initially reported 26 advisories (3 high, 21 moderate, 2 low), including Expo SDK 57 CLI/config, `image-size`, `zod`, and older nested `expo-file-system`/`uuid` under the actively used `expo-music-info-2`. The compatible Metro 0.84.5 patch family removed `image-size`; after SDK 57 patch updates and `expo-system-ui`, live `npm audit` and `npm ci` report 25 (2 high, 21 moderate, 2 low). Offline audit returned zero because its cached advisory data was stale. | Build-tool supply chain plus local device-media metadata parsing. | Remaining high findings are Expo CLI/Zod; npm indicates Expo SDK 58 as the fix. Expo 57 targets React Native 0.86 / React 19.2.3; Expo 58 targets RN 0.88 / React 19.3.0. A major migration needs coordinated native compatibility testing. | Review remaining package advisories individually; maintain an SDK 58 compatibility migration with Android device/build tests. No forced upgrade was used. |
| Critical | **Music rights and third-party provider terms are unresolved.** `Api-cache/music.py` supports provider search and Spotify playlist helpers; downloads/extraction calls Lightning/yt-dlp paths. YouTube terms limit downloading to service-permitted, authorized, or legally allowed cases; Spotify policy has restrictions on integrations, attribution, caching, and stream ripping. | Distribution approval, takedowns, user trust, service stability. | Search metadata and media access are bundled across providers without evidence in this checkout of rights review or an explicit source allowlist. **Inference:** Spotify playlist-to-extractor and YouTube extraction paths require specific review; this is not a legal finding. | Review each provider's current terms, licensing/permissions, attribution, territory rules, and download rights. Disable any unsupported route before public promotion. |
| High | **APKPure binary cannot be matched to source.** No APK found in accessible project tree; no submission hash, version/build, or signing fingerprint. APKPure page was inaccessible to the browser. | Users may install a binary that differs from this checkout; cannot validate patch level. | Release artifacts and provenance are unavailable. | Obtain submitted APK and its recorded metadata; compare hash, package, version/build, signing cert, manifest permissions, source commit, and build workflow. |
| High | **Downloads route remains in the active app.** `SearchScreen.js` requests `/api/downloads/remote/search`; avatar/image upload and download routes also use `/api/downloads/*`. `Api-cache/music.py` reads `B24_DOWNLOADS_SERVICE_URL`. | Search, downloads, uploads, playback resolution. If the old service is shut down or unset, users can receive empty results or 5xx errors. | Service ownership is split between gateway-configured `downloads` and API-cache's own download blueprint/downstream URL. | Check runtime service map and authenticated gateway health; test search/info/fetch/upload against staging and production; document one canonical route. |
| High | **Backend request authentication is inconsistent in source.** `Api-cache/app.py` immediately returns from its global auth hook; download-specific routes have separate internal auth. | Potential unauthenticated access or inconsistent protection depending on route. | Global authentication is explicitly disabled in source; route-level protections vary. | Review deployed source and each route; use explicit allowlists, user authorization, quotas, and independent secret management. Do not infer all endpoints are open from the one hook alone. |
| High | **No automated test or lint suite.** `package.json` defines only Expo start commands. A GitHub Actions workflow exists; the local change runs Expo config and Android JS bundle validation on push, but has not been executed on GitHub. | Regressions in queue transitions, auth, download cancellation, Android native plugins can still pass the bundle check. | Existing public workflow was publish-on-push. Local source now separates validation from manual signed release. | Add deterministic tests/lint and native release validation; configure protected release environment; verify workflow run on GitHub only after approval. |
| Medium | **Search could hang, waste requests after the query changed, allow stale results to replace a newer query, and show failed providers as empty results.** `SearchScreen.js` had unbounded fetches and no latest-request guard; the original timeout helper stopped timing once response headers arrived. | Search responsiveness, mobile data use, backend load, and trust in empty states. | Local fix adds 20-second aborting timeouts that cover JSON body consumption, caller cancellation when a query is replaced/cleared or screen unmounts, latest-request-wins behavior, per-source partial results, and a visible partial-outage message. | Babel parse passed. Targeted helper checks confirmed successful JSON parsing, abort during a stalled response body, and caller cancellation. Current Android JavaScript bundle export passed. Exercise slow/error/out-of-order responses on-device or against a staging mock before release. |
| Medium | **Playback source replacement was keyed only by URI.** The current local playback implementation could leave the wrong player selected when audio/video entries reused a URL, and could retain an outgoing video's resume identity when consecutive queue entries shared a URL. | Player transitions, completion handling, and video resume-position storage. | Local change tracks both URI and media type when deciding to replace a player, and updates the active video identity for same-URI queue entries. | Current Android JavaScript bundle export passed; actual queue/player transition behavior still needs device tests using same-URI audio/video and repeated-URL entries. |
| High | **Update mechanisms overlap.** `app.json` enables Expo Updates; `useOtaCheck.js` checks/downloads a JS update; `otaClient.js` checks native version; `src/updater.js` contains a GitHub APK installer but no caller was found. | Update prompts, installs, runtime compatibility, accidental wrong artifact. | More than one update design remains in source and release/runtime settings are not verified. | Define a single update policy, verify runtime version and channel, check signature/build compatibility, and remove only after confirming unused. Test rollback and failed update on a device. |
| Medium | **Broad Android permissions increase install friction.** Expo config declares media/audio/video, external storage, camera, fine/coarse location, microphone, and `REQUEST_INSTALL_PACKAGES`; the generated prebuild manifest also includes `SYSTEM_ALERT_WINDOW`, `WAKE_LOCK`, `VIBRATE`, network state, and duplicate foreground-service entries. Live wallpaper, barcode camera, weather location, updater install intent, and media playback are present in source. | First-run trust and store review; permissions unrelated to a music-first value proposition can reduce opt-in. The overlay permission's release necessity is not established. | One app aggregates music plus ancillary camera/weather/media functions, a live wallpaper service, and native playback controls. | Inspect the merged release manifest using an Android SDK build; confirm whether `SYSTEM_ALERT_WINDOW` ships in release and trace it to the owning plugin before removing anything. Review request timing and explain each user-granted permission at point of use. |
| Medium | **Existing sessions stored JWTs in general AsyncStorage.** The current local source now stores tokens in Expo SecureStore (`WHEN_UNLOCKED_THIS_DEVICE_ONLY`) and keeps only the non-token profile in AsyncStorage. `authStorage.js` migrates legacy records on read and removes the plaintext token after successful secure storage. | The APKPure submission and already installed versions are unavailable, so they may still retain plaintext tokens. Server-side token revocation and production authentication behavior are unverified. | Added the SDK-matched `expo-secure-store` native module and routed login, startup, API headers, share, sync, profile update, and sign-out storage through `authStorage.js`. Secure storage unavailable/failure is fail-closed. | Mocked tests passed for legacy migration, profile updates, logout, and unavailable-store handling; Expo Android JS bundle passed. Test native storage behavior and upgrade migration on Android/iOS devices, then compare the submitted APK. |
| Medium | **Previously shipped error-reporting code transmitted raw messages and stacks.** The submitted APK is unavailable, so its behavior cannot be verified. The local source now disables reports by default and requires opt-in; reports contain allowlisted error class plus app/OS version, screen, and fatal flag, with no raw message or stack. `Api-cache/client_log.py` prints received fields. | Older installed builds may still send raw exception data; server log retention/access policy remains unverified. | Local `errorReporter.js` change adds opt-in storage and minimizes each report. Settings exposes the control under About & updates. | Runtime checks verified default-off, opt-in/out behavior, and absence of raw message/stack from payload; Android bundle export passed. Verify the submitted APK version and publish privacy/retention disclosures before release. |
| Medium | **Search result and playback success depend on remote services.** App calls Render gateway, which proxies multiple environment-configured services; providers and extraction are external. Gateway `/ping` and API-cache `/` were 200, while `/health` exceeded the audit's 12-second timeout. | Cold starts, provider quotas, service shutdowns, long waits, empty results. | No guaranteed service level or local fallback for remote search. | Observe per-service latency and errors, add timeouts/retry UX/circuit breakers, validate on slow/offline connections and low-memory Android devices. |
| Medium | **Product story is wider than “music app.”** The repository includes music plus news, AI chat, weather, trivia, food, and other screens. | Onboarding and store-page differentiation may be unclear. | General B24 feature set is presented within one product. | Choose a music-first core journey, make ancillary tools secondary, and test first-play completion with new users. |
| Low | **Public GitHub presentation is sparse.** Repository About section has no description/site/topics and visible Releases section is empty. | Developers and prospective testers lack a trustworthy overview/install status. | No product README/release guide on public page. | Local README prepared. Publish it only after owner approval and blocker cleanup. |
| Low | **Historical backup and patch scripts sit alongside active source.** Many `.pre_*`, `.bak*`, and one-off patch files are in repository inventory. | Review noise and accidental edits to stale code. | Iterative project history retained in working tree. | Classify and move/archive only after usage checks; never delete as part of this audit. |

## Product journey review

| Stage | Existing path | Likely friction | Improve / measure |
|---|---|---|---|
| Discovery | GitHub repository and APKPure listing | GitHub has no concise product description; listing state/link not verified. | Accurate listing, screenshots, privacy/install notes, clear state labels for pending vs live. |
| Installation | APK package `com.anonymous.b24sound` per owner-provided APKPure URL; `app.json` now explicitly sets this ID and Expo prebuild config resolves it. | Submitted APK/source identity and signing remain unknown; arm64-only build; install-from-unknown-source and signing trust. | Compare submitted package, signer, versionCode, and hash before any update; use the approved listing only after approval is confirmed. |
| First launch | Root mounts App; account flow can create a backend guest account. The local login UI now discloses this and says a username/password are not required from the user. | Data handling and account recovery remain unclear; there is no verified true anonymous/local mode. | UI disclosure is implemented. Publish the accurate privacy/data and guest-account deletion/recovery information; test the language and screen reader behavior on Android. |
| Discovery | Home and Search combine local/device and remote providers. | Provider-specific availability, permissions, empty/error behavior. | Provider labels, attribution, clear loading/retry/empty states; keep local library useful without network. |
| Playback | Shared audio/video engine; queue and native media controls. | Device/service compatibility, background transitions, seeking, codec and external stream failures. | Test physical devices and lifecycle; record successful first play and 10-minute session, not just taps. |
| Return | Local history, downloads, recommendations, notifications/widgets. | Persistent retention events not available in a privacy-reviewed aggregate dashboard. | Measure opt-in, local-only engagement where possible, D1/D7 returning sessions and playback errors. |

## Immediate blockers before a public launch

- Resolve exposed gateway and signing credentials.
- Establish which downloads/extractor service is deployed and test the entire discovery→playback path.
- Obtain and verify the submitted APK against current source.
- Complete rights/terms/privacy/permission review.
- Create a repeatable Android build and device test matrix.
